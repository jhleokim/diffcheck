# diffcheck — 정비사업 계약서 검토용 대조 도구 (설계 초안)

> 상태: **초안 (draft)** — 구현 전 합의용 문서. 코드는 아직 없음.
> 작성 기준일: 2026-09-03

## 1. 무엇을 만드는가

신탁사가 사업 계약서를 검토할 때, **두 개(이상)의 계약서를 조항 단위로 대조**하고, 그 결과를
**전/후 대비표 Word 문서로 내보내는** 로컬 웹앱.

검토 대상은 도급계약서 하나가 아니다. 신탁계약서 · 공사도급계약서 · 공사도급승계계약서 ·
대출약정서 · 감리/설계 용역계약서를 모두 다루며, **주력은 신탁계약서 · 공사도급승계계약서 ·
용역계약서**다(§2.1). 기존 `jeongbi-contract-review` 스킬은 도급계약서만 다루므로,
**주력 계약서에는 지금 아무 도구도 없다.**

그 스킬이 "무엇을 어떻게 고칠지"를 판단하는 도구라면, diffcheck은 **"실제로 무엇이 달라졌는지"를 놓치지 않고 잡아내는** 도구다. 역할이 다르고 상호 보완적이다.

| | jeongbi-contract-review 스킬 | diffcheck |
|---|---|---|
| 성격 | 판단·법리 검토 (LLM) | 기계적 대조 (결정론) |
| 입력 | 계약서 1건 + 사업조건 | 계약서 2건 이상 |
| 강점 | 수정안 도출, 법리 근거 | 누락 없는 전수 비교 |
| 약점 | 조항 누락·순서 변경을 놓칠 수 있음 | 무엇이 위험한지 스스로 판단 못함 |

**핵심 사용 시나리오**: 시공사가 500페이지짜리 수정본을 보내왔을 때, 사람이 눈으로 훑어서 "몰래 바뀐 한 줄"을 찾는 일을 없앤다.

## 2. 지원할 비교 모드 (6종)

| 모드 | 기준(좌) | 대상(우) | 목적 | 우선순위 |
|---|---|---|---|---|
| **A. 원본 vs 우리 수정안** | 접수 원본 | 검토 수정안 | 산출물 2(전/후 대비표) 자동 생성 | ★ 1순위 |
| **B. 표준계약서 vs 제출본** | 표준계약서·신고약관 | 상대방 제출본 | 독소조항·무단 변경 탐지 | ★ 1순위 |
| **C. 협상 라운드 간 버전 비교** | N차본 | N+1차본 | 회차별 조항 이력 추적 (타임머신) | ★ 1순위 |
| **E. 본문 vs 특약 (override)** | 신탁계약서 본문 | 신탁특약 | **어느 조가 무력화됐나** | ★ 1순위 |
| **D. 과거 사업 계약서 간 비교** | 과거 현장 계약서 | 금번 계약서 | 우리 표준문구 일관성 점검 | 3순위 |
| **F. 문서 간 정합성** | 계약서 N종 | — | 같은 사항의 값이 서로 맞는가 | 2순위 · **별도 엔진** |

A·B·C·D·E는 **한 엔진(순서 보존 정렬)** 으로 처리된다. 모드 F만 성격이 다르다 — §2.2 참조.

모드 C는 2건 비교의 반복이 아니라 **N-way 타임라인**이 되어야 실용적이다(제24조가 1차→2차→3차에서 어떻게 움직였는지 한 줄로 보기). 프로토타입에서 확인한 결과 이것이 검토자에게 가장 값어치 있는 화면이었으므로 **1순위로 올린다.** 상세 설계는 §7.3.

모드 D는 비교라기보다 **문구 라이브러리 조회**에 가깝다. "우리가 쓰는 물가변동 조항 표준문구"를 축적해두고 신규 계약서가 그것과 얼마나 벗어났는지 보는 것. 별도 저장소(문구 DB)가 필요하므로 마지막에 붙인다.

### 2.1 검토 대상은 도급계약서만이 아니다

**초판은 도급계약서에 과적합해 설계했다.** 실제 검토 대상은 신탁계약서 · 공사도급계약서 ·
공사도급승계계약서 · 대출약정서 · 감리용역계약서 · 설계용역계약서 등이며,
**주력은 신탁계약서 · 공사도급승계계약서 · 용역계약서**다. 기존 `jeongbi-contract-review`
스킬은 도급계약서만 다루므로(신탁·승계·대출 언급 0건), 주력 계약서에는 도구가 전혀 없다.

| 유형 | 성격 | 비교 축 | 기준선 |
|---|---|---|---|
| **신탁계약서** | 본문은 금감원 신고 약관 → 거의 불변. **협상은 특약에서** | 모드 **E** (본문↔특약) | 신고 약관 (각 사 공시) |
| 공사도급계약서 | 조문 협상. 표(마감재·하자담보) 있음 | 모드 A·B·C | 국토부 표준계약서 |
| **공사도급승계계약서** | 원계약을 **준용/배제**로 참조 | 모드 C + **참조 해소** | 원 도급계약서 |
| 감리·설계 용역계약서 | 짧고 정형적 | 모드 B·D | 사내 표준문구 |
| 대출약정서 | 이자율·EOD·인출선행조건 | 모드 A·C | — |

**엔진은 유형을 안 가린다.** 조 단위로 쓰인 한국어 계약서면 정렬·판독·트래킹·추출이 그대로
동작한다. 유형별로 달라지는 것은 **위험도 룰셋과 대비표 분류**뿐이며, 이는 §8에서 데이터로 분리한다.

#### 신탁계약서의 2층 구조

실물(한국토지신탁 「토지신탁계약서(관리형)」 25p·35조)에서 확인한 구조:

```
본문 35개 조          ← 금감원 신고 약관. 거의 안 바뀜
별첨1 신탁부동산의 표시
별첨2 우선수익자 및 수익자의 표시
별첨3 이건 사업의 내역 (건축개요 / 주요 건축사양)
별첨4 신탁보수
별첨5 신탁특약        ← 실제 협상은 여기서. 분량은 본문과 비슷
```

> 제35조(신탁계약과 신탁특약의 관계) … **신탁특약의 내용은 이 신탁계약의 내용을 우선한다.**

따라서 신탁계약서에서 본문끼리 diff를 돌리면 대부분 "동일"만 나온다. **필요한 것은
특약이 본문의 어느 조를 뒤집는지 추적하는 것**(모드 E)이며, 특약이 본문만큼 길기 때문에
곁다리 패널이 아니라 **좌우 대조 화면 하나를 온전히 써야 한다.** 상태 라벨만 바꾸면
기존 그리드가 그대로 쓰인다:

| 정렬 결과 | 모드 E에서의 의미 |
|---|---|
| 동일 / 짝 없음(좌) | 특약이 안 건드림 → 본문 그대로 효력 · **접기 대상** |
| 변경 · 번호 이동 | **특약이 본문을 대체함** ← 핵심 검토 대상 |
| 신설(우측 단독) | **본문에 없던 신규 특약** ← 더 위험할 수 있음 |

**접기 기준이 반전된다.** 버전 비교는 `동일`을 접지만, 모드 E는 **`특약이 안 건드린 본문 조`**
를 접는다. 모드 E에는 `동일`이 아예 없다 — 특약 문구가 본문과 같을 리 없기 때문이다.

**모드 E에서는 어절 diff 하이라이트를 꺼야 한다.** 프로토타입에서 켜뒀더니 매칭된 조가
전부 빨강/초록으로 칠해져 읽을 수가 없었다. 특약은 본문을 **고친** 것이 아니라 **다른 문장으로
새로 쓴** 것이라, 어절 diff가 "전부 삭제 + 전부 추가"로 본다. 원문을 그대로 보여주고
거터가 관계만 표시한다.

**검증 결과 (합성 특약 기준): 21쌍 중 17건 정확.** 실물 특약이 아니므로 이 수치는 참고값이다.

**남은 한계 — override는 1:N이다.** 특약 하나가 본문 여러 조를 건드린다(예: 「분양가의 결정 및
분양업무」 특약이 본문 제15조와 제16조를 동시에 대체). 지금 정렬 엔진은 **1:1 매칭만 만들 수
있으므로** 이 경우 한쪽을 놓친다. M2에서 해결할지, 사람이 검수 화면에서 보정하게 둘지 결정 필요.

#### 신탁계약서가 다른 계약서들의 허브다

본문에 다른 계약서를 부르는 조항이 박혀 있다. 계약서 목록이 왜 그 조합인지가 여기서 나온다.

- **제11조(공사도급계약)** — 시공사와 도급계약 체결, **"위탁자가 이미 체결한 공사도급계약이
  있는 경우 이를 승계할 수 있다"** ← 공사도급승계계약서의 출처. ③항에 시공사 **책임준공의무**
- **제12조(설계·감리 등 용역계약)** — 마찬가지로 승계 조항 ← 용역계약서의 출처
- **제13조(자금조달)** — 위탁자 조달 원칙, 미달 시 시공사 **신용보강·자금지원** ← 대출약정서와 맞물림

### 2.2 문서 간 정합성은 정렬 문제가 아니다 (실험으로 확인)

모드 F를 기존 엔진으로 처리할 수 있는지 실물로 시험했다. 신탁계약서 35조 각각에 대해
도급계약서 43조 중 최유사 조를 찾은 결과:

```
★ 0.46  신탁 제2조(용어의 정의)        ↔ 도급 제2조(정의)          맞지만 무의미
★ 0.44  신탁 제20조(신탁건물 하자담보)  ↔ 도급 제31조(하자담보)      맞음
★ 0.38  신탁 제34조(관계법령의 준수)    ↔ 도급 제40조(법령의 준수)   맞음
  0.22  신탁 제11조(공사도급계약)      ↔ 도급 제32조(건설공사의 하도급) 헛매칭
  0.22  신탁 제9조(수익권의 양도)      ↔ 도급 제38조(채권양도)      헛매칭

0.25 이상: 3건 / 35건
```

> 위 수치는 §3.1의 문자 n-gram 유사도로 다시 잰 것이다. 어절 코사인일 때는 2건이었고
> `관계법령의 준수`↔`법령의 준수`가 0.17에 묻혀 있었다. n-gram이 정답 2건을 건져냈지만
> **3/35는 여전히 쓸 수 있는 수준이 아니고, 헛매칭도 그대로 남는다.**

**세 가지 이유로 구조적으로 실패한다:**

1. **같은 사항을 다른 어휘로 쓴다.** 신탁계약서는 `수탁자/위탁자`, 도급계약서는 `도급인/수급인`.
   같은 준공 얘기를 해도 어휘가 겹치지 않는다.
2. **길이 편향.** 길고 어휘가 다양한 조항(도급 제22조)이 여러 신탁 조항의 "최유사"로 반복 등장한다.
3. **순서 보존이 성립하지 않는다** → NW를 쓸 수 없다. 대응 조항이 앞에 있을 수도 뒤에 있을 수도 있다.

이 실험이 §3.1의 유사도 함수를 문자 n-gram으로 바꾸게 만든 출발점이기도 하다. 다만
n-gram으로 바꾼 뒤에도 **3/35에 그친다** — 조사 문제는 풀렸지만 `수탁자`↔`도급인`이라는
어휘 체계 차이는 그대로이기 때문이다.

**그러므로 모드 F는 조항을 짝짓는 것이 아니라 항목에서 출발한다.** 점검 항목을 룰로 먼저
정의하고, 각 문서에서 키워드로 해당 조항을 찾아 **값을 뽑아 대조**한다.

```yaml
# rules/cross-check.yaml
- id: 책임준공
  문서: [신탁계약서, 도급계약서, 대출약정서]
  키워드: [책임준공, 준공인가, 사용승인, 준공기한]
  추출: [기한, 예외사유]
- id: 시공사_신용보강
  문서: [신탁계약서, 대출약정서]
  키워드: [신용보강, 자금지원, 연대보증, 자금보충]
```

결과는 diff 그리드가 아니라 **정합성 매트릭스**다:

```
항목        신탁계약서      도급계약서        대출약정서
책임준공    제11조③        제10조            제7조(EOD)
            불가항력만 예외  민원 시 연장 가능  ⚠ 예외사유 불일치
신용보강    제13조 단서     —                제12조
```

어떤 항목을 점검할지는 **알고리즘이 발견하지 못한다.** 도메인 지식이므로 룰 파일에 사람이
넣어야 하고, 한 번 넣으면 모든 사업에 재사용된다.

## 3. 진짜 어려운 부분은 diff가 아니라 정렬이다

이 프로젝트의 성패는 여기서 갈린다. 먼저 짚고 간다.

계약서 비교를 `diff a.txt b.txt` 로 하면 반드시 실패한다. 이유:

1. **조 번호가 밀린다.** 시공사가 제24조의2를 신설하면 그 아래 모든 조 번호가 한 칸씩 밀린다. 번호로 맞추면 25조부터 전부 "변경됨"으로 나온다 → 실제 변경 3건이 40건으로 보이고, 사람은 리포트를 안 보게 된다.
2. **조항 순서가 바뀐다.** 장(章) 구성을 재배치하는 경우가 있다.
3. **조사·어미 변화가 노이즈다.** "공사비를 조정한다" vs "공사비는 조정하기로 한다" — 문자 diff는 이걸 전면 재작성으로 표시한다.
4. **표(表)가 많다.** 공사비 내역, 마감재 사양표. 표는 문장이 아니라 **셀 단위**로 비교해야 한다.
5. **줄바꿈·공백이 포맷마다 다르다.** HWPX와 PDF에서 같은 문장이 다르게 떨어진다.

그래서 파이프라인을 **파싱 → 정규화 → 정렬 → diff** 4단으로 분리하고, 정렬 단계를 독립 모듈로 둔다.

### 3.1 조항 정렬 알고리즘 (제안)

```
1단계  순서 보존 전역 정렬 (Needleman-Wunsch)
        s(a,b) = min(1, 명시참조보너스
                        + 0.35·제목 포함도(2-gram)
                        + 0.65·본문 코사인(3-gram))   ← 번호 근접도를 넣지 말 것
        GAP = 0.40 (한쪽을 비우는 비용)
        전부 로컬 계산 (외부 API 없음)
2단계  s < 0.25 로 짝지어진 쌍은 분리 → 삭제(좌측 단독) + 신설(우측 단독)
3단계  사람이 화면에서 매칭을 수정할 수 있어야 한다  ← 필수
```

**유사도는 어절이 아니라 문자 n-gram으로 재야 한다.** 어절 토큰은 한국어 조사 때문에 무너진다 —
`관할법원` ↔ `관할법원의 특례` 가 **0.000**이 나온다. 완벽한 정답 쌍인데 0점이다.
그리고 제목은 코사인이 아니라 **포함도(containment)** 를 쓴다. 본문(415자)과 특약(82자)처럼
길이가 크게 다를 때 코사인이 구조적으로 낮게 나오기 때문이다.

**명시 참조 보너스(+0.5)**: 특약과 승계계약서는 `"신탁계약 제11조에도 불구하고"` 처럼 본문 조를
직접 인용한다. 이보다 확실한 근거가 없으므로 점수를 크게 올린다.

측정 (모드 E, 합성 특약 21쌍 기준):

| 유사도 함수 | 정답 쌍 평균 | 0.25 이상 |
|---|---|---|
| 어절 코사인 | 0.134 | 1 / 21 |
| 문자 3-gram 코사인 | 0.249 | 10 / 21 |
| 3-gram + 제목 포함도 | 0.431 | 17 / 21 |
| **+ 명시 참조 보너스 (채택)** | — | **17 / 21** |

**버전 비교는 회귀 없이 100% 유지된다**(42/42, 43/43, 44/44, 43/43). 한 함수가 모든 모드를 처리한다.

**탐욕적 매칭(각 조마다 남은 것 중 최고점을 고름)은 반드시 실패한다.** 프로토타입에서
탐욕법으로 구현했다가 정확도 39/42가 나왔고, 원인을 추적하니 한 번의 오매칭이 연쇄됐다:

```
제25조(기성부분금)  → 제25조(손해의 부담)   0.30  ← 삭제인데 번호가 같다는 이유로 오매칭
제26조(손해의 부담) → 제26조(부분사용)      0.31  ← 연쇄
제27조(부분사용)   → 제27조(준공검사)      0.32  ← 연쇄
제28조(준공검사)   → 짝 없음 = 삭제로 오판
```

**번호 근접도 항을 점수에 넣으면 안 되는 이유도 여기서 나온다.** 조항이 삭제돼 번호가
밀린 직후에는 "번호가 같으니 맞다"가 정확히 틀린 신호다. 순서 정보는 NW의 순서 보존
제약이 이미 담당하므로 점수에 중복해서 넣을 필요가 없다.

NW로 바꾸자 **네 라운드 모두 100%**가 됐다(42/42, 43/43, 44/44, 43/43). 전체 점수를
최적화하므로 "한 조를 삭제로 두고 나머지를 제자리에 맞추는" 쪽이 이기기 때문이다.
검증 코드는 `experiments/timemachine/src/aligner.reference.js`.

4단계를 빼면 안 된다. 자동 정렬은 90%만 맞고, 나머지 10%를 사람이 못 고치면 도구를 신뢰하지 않게 된다. **정렬 결과 검수 화면이 이 앱의 핵심 UX다.**

> **선행 POC (2026-09-03)**: 회사 실제 계약서를 구하기 전, 공공기관이 공개 배포한 표준계약서(민간건설공사 표준도급계약서, 실제 조 43개)로 위 앵커+유사도 정렬을 최소 검증했다. 조 번호가 전부 밀리는 최악 케이스에서 오탐 0건. 다만 원본이 정비사업 계약서가 아니고 "수정안"도 인위 합성이라 M1 완료 기준을 대체하진 않는다. 상세: `experiments/poc-alignment/README.md`.

### 3.2 diff 3단 계층

정렬된 조 쌍 안에서만 diff를 돌린다.

```
조(Article) 단위   → 신설 / 삭제 / 변경 / 동일
  └ 항(Paragraph)  → 항 단위 정렬 후 diff
      └ 문장 단위   → 어절(띄어쓰기) 토큰 diff
```

한글 노이즈 억제: 어절 토큰 diff를 기본으로 하되, **"조사만 다른 어절"은 경미(minor) 변경으로 별도 표시**한다. 형태소 분석기(kiwi 등) 도입은 선택지로 남기되, 의존성이 무거우므로 M1에서는 조사 목록 기반 휴리스틱으로 처리하고 효과를 본 뒤 결정.

## 4. 공통 중간표현 (CDM)

포맷이 4종이므로, **모든 파서는 동일한 JSON 구조를 뱉는다.** 정렬·diff·내보내기는 원본 포맷을 전혀 모른다. 이 경계가 설계의 중심이다.

```jsonc
{
  "meta": {
    "source_file": "도급계약서_시공사제출본.hwpx",
    "format": "hwpx",
    "parsed_at": "2026-09-03T10:00:00+09:00",
    "confidence": 0.95        // PDF/HWP는 낮게 나옴 → UI에 경고 표시
  },
  "nodes": [
    {
      "id": "art-24",
      "uid": "clause-7f3a",    // 회차가 바뀌어도 유지되는 조항 동일성 (§7.3 타임머신의 전제)
      "type": "article",       // chapter | article | paragraph | item | subitem | table
      "number": "제24조",
      "number_norm": 24,       // 정렬용 정규화 번호
      "title": "물가변동으로 인한 계약금액의 조정",
      "text": "...",           // 하위 노드 텍스트 합본 (정렬 유사도 계산용)
      "children": [ /* 항 */ ],
      "source_span": { "section": 0, "para_start": 412, "para_end": 431 }
    },
    {
      "id": "tbl-3",
      "type": "table",
      "caption": "마감재 사양표",
      "cells": [["구분","사양","비고"], ["바닥","강마루","..."]]
    }
  ]
}
```

`source_span`을 반드시 유지한다. "원본 몇 페이지에 있던 조항인가"를 UI와 대비표에서 되짚어야 하기 때문.

`uid`는 파싱 시점에 새로 발급하고, **회차 간 정렬 결과로 이어붙인다**(v1의 제18조와 v2의 제19조가
같은 조항으로 정렬되면 uid를 승계). 이것이 §7.3 조항 계보의 유일한 근거이므로, 정렬이 틀리면
계보도 틀린다 — §7.4의 신뢰도 표시가 계보 화면에도 따라붙어야 한다.

## 5. 포맷별 파싱 전략과 난이도

| 포맷 | 방식 | 난이도 | 구조 복원 신뢰도 | 비고 |
|---|---|---|---|---|
| **HWPX** | ZIP 해제 → `Contents/section*.xml` (OWPML) 파싱 | 중 | 높음 | **브라우저에서도 가능**(§5.3). 표·스타일 정보까지 살릴 것 |
| **DOCX** | `python-docx` / ZIP → `word/document.xml` | 하 | 높음 | 가장 안정적. **브라우저에서도 가능**(§5.3). 내보내기도 이 포맷 |
| **HWP (구버전)** | CFB 컨테이너 + 압축 레코드 스트림 | **상** | 중 | 파이썬 생태계가 빈약. 아래 별도 논의 |
| **PDF** | `pdfplumber`(MIT), 텍스트 레이어 없으면 OCR | **상** | 낮음 | 조항 구조를 좌표·폰트크기로 추정해야 함. **PyMuPDF는 AGPL이라 배제** — §12.4 |

### 5.1 HWP 구버전 — 권고안

구버전 `.hwp` 바이너리 파서는 유지보수 부담 대비 효용이 낮다. 3단 폴백을 제안한다:

1. **기본 방침**: 사용자에게 "한글에서 `.hwpx`로 다시 저장" 안내 (실무상 대부분 가능)
2. **자동 변환 시도**: 한글이 설치된 PC라면 변환 스크립트 연동 (Windows COM 자동화)
3. **최후**: best-effort 텍스트 추출 후 `confidence: 0.5` 로 표시하고, 정렬 검수 화면을 강제로 거치게 함

이 결정은 되돌릴 수 있으니, 우선 1번만 구현하고 실제로 구버전 파일이 얼마나 들어오는지 보고 판단하자.

### 5.2 PDF — 권고안

PDF는 **비교의 기준(좌)으로만 쓰고, 대비표 생성의 대상(우)으로는 쓰지 않는다**고 선을 긋는 편이 낫다. 구조 복원이 불완전한 문서를 근거로 "제24조 제3항이 이렇게 바뀌었다"고 문서화하면 신뢰 사고가 난다. OCR은 M4 이후.

라이브러리는 **`pdfplumber`(MIT)로 확정한다.** 성능은 PyMuPDF가 낫지만 PyMuPDF는 `AGPL-3.0 or Artifex Commercial` 듀얼 라이선스여서, 사내 보안·법무 검토에서 논쟁을 만든다. 우리 처리량(계약서 수백 페이지)에서는 성능 차이가 체감되지 않으므로 라이선스 안전성을 택한다.

### 5.3 hwpx·docx는 브라우저에서 바로 열린다

프로토타입에서 확인한 사실: **hwpx와 docx는 둘 다 ZIP + XML**이므로, JSZip 하나로
브라우저에서 직접 판독된다. 파일을 서버로 보내거나 별도 변환기를 거칠 필요가 없다.

| 형식 | 경로 | 텍스트 |
|---|---|---|
| `.hwpx` | ZIP → `Contents/section*.xml` (OWPML) | `<hp:t>` 수집, `</hp:p>`에서 줄바꿈 |
| `.docx` | ZIP → `word/document.xml` | `<w:t>` 수집, `</w:p>`에서 줄바꿈 |

이는 §6의 "파싱은 파이썬 백엔드" 구조를 부정하지 않는다. 백엔드가 정본이고, 브라우저
판독은 **드래그앤드롭으로 즉시 버전을 추가하는 경로**에 쓴다(§7.7).

> **hwpx 함정**: 한글은 글자 서식이 바뀌면 한 문단 안에서도 `<hp:t>` 런이 쪼개진다.
> 런 단위로 줄을 나누면 `"도급인과 / 수급인은"` 처럼 조문이 끊긴다. **문단(`</hp:p>`)
> 기준으로만 줄을 나눌 것.**

**스택 선택 근거**
- 백엔드 Python: hwpx/docx/pdf 파싱, docx 생성, 유사도 계산이 전부 파이썬 생태계에 있음. 스킬의 기존 스크립트와도 이어짐.
- 프론트 React + Vite: 좌우 스크롤 동기화, 가상 스크롤(1000조항), 인라인 편집이 필요해서 vanilla로는 금방 한계. 다만 **빌드 산출물을 레포에 커밋**해서 `pip install` 만으로 실행되게 한다(검토자 PC에 Node 요구 X).
- 실행: `diffcheck serve` → 브라우저 자동 오픈.

### 6.1 보안 원칙 (타협 없음)

계약서는 전량 대외비다.

- 서버는 **127.0.0.1 에만 바인딩**. 외부 노출 옵션 자체를 제공하지 않는다.
- **외부 네트워크 호출 없음**이 기본값. 유사도 계산도 로컬 TF-IDF로 하고 임베딩 API를 쓰지 않는다.
- 업로드 파일은 사용자가 지정한 작업 폴더에만 저장. 임시 디렉터리에 잔재를 남기지 않는다.
- LLM 연동(변경 요약 자동 생성 등)은 **명시적 opt-in**으로만. 기본 꺼짐, 켤 때 "본문이 외부로 전송됨" 경고.
- 프론트 번들에 **CDN 참조가 하나도 없어야 한다** (폰트·아이콘·라이브러리 전부 로컬). §12.2 참조.

## 7. 화면 설계

> 이 절은 **실제로 만들어보고 다시 쓴 것**이다. 초판은 실물 없이 상상으로 쓴 탓에 도구가 아니라
> 대시보드가 나왔다. 프로토타입: `experiments/timemachine/`

### 7.0 가장 중요한 구조 결정: 좌우를 한 개의 그리드로 그린다

**좌/우를 각각 독립 스크롤 패널로 만들지 않는다.** 대신 **3열 CSS 그리드 한 개**
(`좌 조문 | 거터 | 우 조문`)를 쓰고, **정렬쌍 하나가 그리드의 한 행**이 된다.

```
grid-template-columns: 1fr 46px 1fr;
행 1 = [원본 제17조] [ = ] [수정안 제18조]
행 2 = [  (빈 자리) ] [ + ] [수정안 제18조의2]
행 3 = [원본 제18조] [ ~ ] [수정안 제19조]
```

이 하나의 결정이 세 가지 문제를 동시에 없앤다:

| 문제 | 별도 패널 방식 | 단일 그리드 방식 |
|---|---|---|
| 좌우 행 높이 정렬 | JS로 높이 측정·동기화 필요, 폰트 로딩·리플로우마다 깨짐 | 그리드가 자동으로 맞춤 |
| 스크롤 동기화 | 양쪽 scrollTop 상호 반영, 튐 현상 대응 필요 | 스크롤 컨테이너가 하나뿐이라 **불필요** |
| 좌우 동시 하이라이트 | 인덱스 매핑이 어긋나면 엉뚱한 조가 켜짐 | 같은 행의 세 셀에 클래스만 붙임, **구조적으로 항상 정확** |

짝이 없는 조항(신설/삭제)은 반대편 셀을 비우지 않고 **`이 회차에 없음` 자리표시**를 넣는다.
그래야 시선이 갈 곳을 잃지 않고, 행 정렬도 유지된다.

> 구현 주의: 행 인덱스를 `자식위치 / 3`으로 계산하면 안 된다. 아래 7.2의 접힘 밴드는 자식
> 1개만 차지하므로 산술이 깨진다. 프로토타입에서 실제로 이 버그가 나왔다. **각 셀에 `data-row`
> 속성을 박고 그것으로 찾을 것.**

### 7.1 마우스오버 실시간 트래킹 + 좌우 동시 하이라이트 ★필수

클릭해서 펼치는 방식은 계약서 검토에 맞지 않는다. 검토자는 자를 대고 훑어 내려가지, 한 건씩
열어보지 않는다. 따라서 **hover가 곧 주 조작**이다.

- `mousemove`를 `requestAnimationFrame`으로 스로틀 (매 이벤트마다 DOM 작업 금지)
- 커서 Y를 따라 **가로 자(ruler)** 를 양쪽 패널에 걸쳐 그린다
- 커서 아래 행의 **좌·거터·우 세 셀에 동시에** 형광 밴드를 입힌다
- 하단 **상태바가 연속 갱신**된다:
  `제18조 ↔ 제18조 │ 내용 변경 · 신뢰도 0.99 · 추가 2곳 · 삭제 2곳`
- 클릭은 2차 조작: 본문 클램프 해제(전문 펼치기). hover와 충돌하지 않는다.

형광색은 diff의 빨강/초록과 **의미가 겹치면 안 된다**. 빨강=삭제, 초록=추가, 노랑=지금 보고
있는 곳. 검토자가 형광펜을 긋는 실제 행위와 같은 의미다.

### 7.2 동일 구간 접기

계약서는 대부분의 조가 그대로다. 접지 않으면 변경점이 스크롤 한참 아래에 묻힌다.
연속된 `동일` 행이 3개 이상이면 한 줄로 접는다 (Diffchecker의 unchanged-lines 방식).

```
▸ 동일한 조 10개   제1조–제10조
```

프로토타입에서 이걸 넣자 제18조의 `응하여야 한다 → 응할 수 있다`(의무→임의 전환)가
**첫 화면에서 바로** 보였다. 넣기 전에는 스크롤을 한참 내려야 했다. 체감 차이가 가장 컸던 기능.

본문은 4줄로 클램프(`-webkit-line-clamp`)하고 클릭 시 전문. 클램프 없이는 조문 하나가
화면 절반을 먹어 훑기가 불가능하다.

### 7.3 타임머신: 회차 이력 ★필수

macOS Time Machine의 은유를 협상 회차에 그대로 대응시킨다.

**우측 레일 = 회차 타임라인.** 각 노드에 `회차명 · 날짜 · 작성주체(발주처/시공사) · 조 개수`.
노드를 클릭하면 그 회차의 대조로 이동한다.

**조항별 계보 = 타임머신의 깊이.** 조문에 마우스를 올리면 레일 하단에 **그 조항이 전 회차에서
어떻게 움직였는지**가 쌓인다:

```
부적합한 공사 등
 원안   제18조  ████████
 1차    제18조  ███████        ← 의무조항이 임의조항으로 바뀐 회차
 2차    제18조  ████████       ← 되돌림
 최종   제18조  ████████
```

이것이 검토자에게 가장 값어치 있는 화면이다. "이 조항이 협상 과정에서 언제 무너졌고 언제
되찾았는지"는 지금 어떤 도구로도 안 보인다. 조항의 **동일성(uid)** 을 회차 간에 유지해야
가능하므로, CDM(§4)에 조항 uid를 넣고 회차 간 정렬 결과로 uid를 이어붙인다.

### 7.4 정렬 신뢰도를 숨기지 않는다

자동 정렬은 틀린다. 프로토타입 검증에서 조항 삭제와 번호 밀림이 겹친 회차는
**39/42**였다(3건 오정렬).

- 상단에 라운드별 `정렬 39/42 · 검수필요 3` 상시 표시
- 신뢰도가 낮거나 검증 실패한 행은 **거터에 노란 표시**
- 이 표시가 §3.1의 "사람이 매칭을 고치는 단계"로 들어가는 입구가 된다

틀릴 수 있다는 사실을 감추면 검토자는 도구를 신뢰하지 않는다. 어디를 봐야 하는지 알려주는 쪽이 낫다.

### 7.5 나머지 화면

**S1 업로드** 좌/우 파일 드롭 + 비교 모드(A~D). 파싱 신뢰도 즉시 표시(§5의 `confidence`).

**S2 정렬 검수** 낮은 신뢰도 매칭을 상단에 모아 보여주고 드래그로 수정·해제·수동 연결.
7.0의 그리드를 그대로 쓰되 편집 가능 상태.

**S4 검토 코멘트** 각 변경 건에 `수정 사유 / 법리근거 / 우선순위(Must·Should·Nice)`.
대비표(§9)의 마지막 컬럼이 여기서 채워진다. 자주 쓰는 사유는 스니펫으로 재사용.

**S5 내보내기** 선택한 건만 골라 대비표 생성 → 미리보기 → `.docx`.

### 7.6 시각 언어 (AI 티 나는 기본값 회피)

| 회피 | 채택 |
|---|---|
| Inter 등 도구 기본 폰트 | JetBrains Mono(거터·번호·날짜 — 자릿수 정렬이라는 기능적 필연) + Noto Serif KR(조문 — 법률문서 관행) + IBM Plex Sans KR(UI) |
| 장식용 보라-파랑 그라데이션 | 의미론적 색상만: `--sem-removed / --sem-added / --sem-moved / --sem-track`. 각 색이 상태 하나를 전담 |
| 모든 요소 동일 radius·padding | **다크 앱 크롬(도구) + 라이트 문서 패널(종이)** 로 위계를 만든다. 문서 영역엔 카드·그림자를 쓰지 않고 헤어라인만 |
| 큰 숫자 타일 대시보드 | 상단 바에 `−1 +1 ~20` 인라인 집계 (Diffchecker 관행) |
| 아무 것도 안 하는 hover | hover가 곧 핵심 기능(7.1) |

### 7.7 버전 추가 · 검토본 · 대비표

**버전 추가.** 좌측 레일이 곧 타임라인이다. 드래그로 순서를 바꾸고, 버전 사이 드롭존에
놓아 **중간에 끼워넣는다**. 파일은 레일 하단 드롭존에 떨어뜨리고(§5.3), 텍스트는 붙여넣기
모달로 넣는다. 조 인식은 `제N조(제목)` 정규식.

구버전 `.hwp`·`.doc`과 `.pdf`는 **받되 거절하고 방법을 알려준다** — "한글에서 열고
[다른 이름으로 저장] → 형식을 «한글 문서 (*.hwpx)»로". 조용히 실패하지 않는 것이 중요하다.

**검토본.** "최종본"이라 부르지 않는다. 검토 중에는 무엇이 최종이 될지 모른다.
변경 건마다 `좌 채택 / 우 채택 / 제외`를 고르면(동일한 조는 자동 계승) `검토본 N차`가
타임라인 끝에 추가된다.

**최종본 지정은 별개의 상태다.** 모든 버전 카드에 ☆가 있고, 누르면 그 버전이 최종본이
된다(항상 하나만, 언제든 이동·해제). 원본이든 시공사 제출본이든 검토본이든 지정할 수 있다.
"생성"과 "확정"을 분리해야 실무와 맞는다.

**대비표.** 레일에서 버전 2개를 체크 → 미리보기 → `.docx`. §9 규격 그대로.

## 8. 도메인 룰: 위험도 자동 태깅

범용 diff 도구와 diffcheck을 가르는 지점. 변경된 조항에 키워드·패턴 룰을 걸어 자동으로 등급을 매긴다.

### 8.1 유형 무관 — 문구 변화의 의미를 잡는 패턴

계약서 종류를 가리지 않고 적용된다. 어절 diff 결과 위에서 판정한다.

- 의무 → 임의: `"하여야 한다" → "할 수 있다"`
- 주체 전환: 의무 주체가 바뀜 (책임 이전)
- 한정어 삽입: `"중대한", "불가피한", "상호 협의하여"` 신규 삽입
- 수치 변경: 임계치·기간·비율의 변화 (숫자 토큰 비교, §8.3)
- 고유명사 소실: `강마루(동화 나투스진) → 강마루` (사양 하향의 전형)
- 구속력 완화: `"A社 제품" → "A社 제품 또는 동등품"`

### 8.2 유형별 룰셋 — 코드가 아니라 데이터

§2.1의 계약서 유형마다 관심사가 다르므로 룰셋을 분리한다. 파일 업로드 시 조 제목으로
유형을 자동 판별해 해당 룰셋을 붙인다.

```
rules/
  common.yaml       §8.1 패턴 (유형 무관)
  dogeup.yaml       물가변동, 공사비 검증, 품질사양서, LD, 지체상금
  sintak.yaml       신탁보수, 신탁기간, 우선수익권 순위, 해지사유, 특약 우선
  seunggye.yaml     승계범위, 채무인수, 하자책임 승계, 준용/배제
  yongyeok.yaml     용역범위, 성과품 귀속, 재위탁, 지연배상
  daechul.yaml      이자율, 기한이익상실(EOD), 인출선행조건(CP), 담보
  cross-check.yaml  §2.2 문서 간 정합성 점검 항목
```

기존 도급계약서 등급표는 `dogeup.yaml`로 옮긴다:

| 등급 | 트리거 예시 (도급계약서) |
|---|---|
| **★ 최우선** | 물가변동, 계약금액 조정, 공사비 검증, 정비사업지원기구, 착공, 사업시행계획인가 |
| ● 중요 | 계약보증금, 하자담보, 손해배상 예정, 지체상금, 품질사양서, 동등품 |
| ○ 확인 | 통지, 기한, 협의, 준용 |

### 8.3 방향 판정은 코드에 넣지 않는다

수치가 바뀌었을 때 **어느 방향이 발주처에 불리한가는 항목마다 다르고, 짐작하면 틀린다.**
(자재가격 연동 기준 비율만 해도 상향이 누구에게 유리한지 자명하지 않다.)

따라서 코드는 **변화와 폭만 계산**하고(`24개월 → 12개월 (−50%)`), 유불리 판정은
룰 파일에 도메인 전문가가 명시한 것을 읽기만 한다. 룰에 없으면 "수치 변경"으로만 표시하고
판정하지 않는다 — **틀린 판정보다 판정 없음이 낫다.**

모든 룰은 `rules/*.yaml` 로 데이터화해 코드 수정 없이 늘린다.

## 9. 내보내기 — 산출물 2 규격 준수

스킬 `assets/template_comparison.md` 의 규격을 그대로 따른다. 이걸 지켜야 기존 검토 문서와 섞어 쓸 수 있다.

- A4 **가로(landscape)**
- 컬럼: `No.(A-1 형식) | 조항 | 【전】원본 | 【후】수정 제안 | 수정 사유/법리근거`
- 색상: 헤더 `#1F3A5F`(흰 글씨) / 원본셀 `#FFF5F5`(강조 `#C00000`) / 수정안셀 `#F0F8E8`(강조 `#0070C0`) / 사유셀 `#FFFEF0`
- 카테고리 A~D 끝마다 "처리 핵심" 강조박스
- 셀 안에서 변경된 어절만 굵게/색으로 강조 (diff 결과를 그대로 서식에 반영 — 손으로 만들 때 가장 귀찮은 부분이 자동화됨)

부가 산출물로 `changes.json`(전체 변경 원장)과 `summary.csv`를 함께 뱉는다. 후자는 협상 회차별 진행 관리에 쓴다.

### 9.1 브라우저에서 .docx를 만드는 법

cdnjs에 docx 라이브러리가 없으므로 **JSZip으로 OOXML을 직접 조립**한다. Word가 여는 데
필요한 최소 구조는 세 파일뿐이다:

```
[Content_Types].xml
_rels/.rels
word/document.xml     ← 본문 + <w:sectPr>
```

- 가로 A4: `<w:pgSz w:w="16838" w:h="11906" w:orient="landscape"/>`
- 셀 배경: `<w:shd w:val="clear" w:fill="FFF5F5"/>` — §9의 색상을 그대로 넣는다
- 글자 색: `<w:color w:val="C00000"/>`
- XML 이스케이프 필수 (`&`, `<`, `>`, `"`)

검증됨: `file` 명령이 `Microsoft Word 2007+`로 인식, 세 XML 파트 모두 파서 통과, 가로 A4
지시 확인. **다만 실제 Word 렌더링은 미확인** — M3에서 반드시 확인할 것.

아티팩트/브라우저에서 파일을 건네는 경로는 `downloads` 능력(§12.3)을 쓰고, 없으면
`<a download>`로 폴백한다.

## 11. 아직 결정 안 한 것

1. **구버전 HWP를 정식 지원할 것인가** — 실제 유입 비율을 보고 M4에서 결정 (§5.1)
2. ~~**형태소 분석기 도입**~~ — **대체로 결정됨.** 조사 문제는 **문자 n-gram으로 해결됐다**(§3.1).
   어절 토큰에서 0.000이던 `관할법원`↔`관할법원의 특례` 가 정상 매칭되고, override 정확도가
   1/21 → 17/21로 올랐으며 버전 비교는 회귀가 없다. 형태소 분석기 의존성을 지지 않아도 된다.
   다만 §2.2의 **문서 간 매칭은 형태소 분석으로도 해결되지 않는다**(`수탁자`↔`도급인`처럼 어휘
   체계 자체가 다름) — 그건 별도 엔진으로 간다.
3. ~~**LLM 연동 범위**~~ — **결정됨(2026-09-03).** 어댑터 인터페이스만 두고 실제 연동은 보류. 근거·재검토 조건은 §12.3
4. **모드 D 문구 DB 스키마** — 과거 계약서를 몇 건이나 적재할지, 조항 단위 색인 방식
5. **다중 사용자** — 현재 설계는 1인 로컬 전용. 팀 공유가 필요해지면 아키텍처가 달라짐 (지금은 하지 않는 쪽 권장)
6. **jeongbi 스킬과의 연동 방향** — diffcheck의 `changes.json` 을 스킬이 읽어 검토의견서를 쓰는 구조가 자연스러움. 인터페이스는 M3 이후 확정

## 12. 오프라인(폐쇄망) 운영 요건

신탁사 내부망은 대개 폐쇄망이다. **오프라인 동작은 나중에 대응할 사항이 아니라 M0부터의 기본 전제**로 둔다. 뒤에 붙이면 CDN 의존이 코드 곳곳에 박혀서 걷어내기 어렵다.

### 12.0 결론: 성능 저하는 사실상 없다

파이프라인에 네트워크 왕복이 하나도 없으므로 처리 속도는 오히려 온라인보다 빠르다.

| 구성요소 | 네트워크 차단 시 | 근거 |
|---|---|---|
| HWPX·DOCX 파싱 | 영향 없음 | ZIP+XML 로컬 처리 |
| 조항 정렬 (TF-IDF) | 영향 없음 | 순수 파이썬 구현, 임베딩 API·scikit-learn 미사용 (§12.1) |
| 3단 diff | 영향 없음 | 문자열 연산 |
| 위험도 룰 태깅 | 영향 없음 | YAML 키워드 매칭 |
| docx 대비표 내보내기 | 영향 없음 | python-docx 로컬 |
| 웹 UI | 영향 없음 (§12.2 준수 조건) | 로컬 번들 |
| PDF OCR | 사전 설치 시 영향 없음 | tesseract + kor 언어팩은 로컬 바이너리 |
| LLM 보조 기능 | 사용 불가 | §12.3 — 애초에 opt-in 부가기능 |

정렬 품질의 상한도 낮아지지 않는다. TF-IDF가 부족해 임베딩이 필요해지면 `sentence-transformers` 로컬 모델(400MB 내외) 파일을 반입해 쓰면 되고, API가 필요 없다. 다만 그 시점엔 배포 용량이 한 자릿수 MB에서 수백 MB로 뛰므로, **채택 전 §12.1의 용량 예산을 다시 검토해야 한다.**

> 참고: 이 도메인에서는 TF-IDF가 유독 잘 맞을 것으로 본다. 계약서 조항은 법률 용어가 고정적이라 어휘 중복 자체가 강한 신호다. 임베딩이 이기는 건 "같은 의미를 완전히 다른 말로 쓴" 경우인데, 계약서에서 조항을 통째로 재작성하는 일은 드물다. **다만 이는 추론이며 실측이 아니다** — M1 실물 검증 항목.

### 12.1 진짜 걸림돌은 성능이 아니라 설치다 — 배포 패키지 설계

폐쇄망 PC에서 `pip install` 이 안 된다. 실무에서 사람을 막는 지점은 여기다.

> **대상 환경 확정 (2026-09-03)**: 검토 PC에 **Python 미설치**, OS는 **Windows 10 / 11** 혼재.
> 이건 새로운 문제가 아니라 애초에 §12.1의 "Python embeddable" 선택이 정확히 이 상황을 겨냥한 것이다 — 검토자 PC에 Python이 있을 거라 가정하지 않는다.
> `win_amd64` wheel과 embeddable 런타임은 Win10·11 양쪽에서 동일하게 동작한다(둘 다 x64 데스크톱 Windows이므로 빌드를 나눌 필요 없음). 32비트 PC가 섞여 있다면 별도 `win32` 빌드가 필요하니 확인 필요.

#### 실측 용량 (win_amd64 / Python 3.11, 2026-09-03 기준)

| 구성 | 크기 | 패키지 수 |
|---|---:|---:|
| **A. 코어** — fastapi, uvicorn, python-docx, lxml, jinja2, python-multipart + 의존성 | **7.4 MB** | 18 |
| B. PDF 추가 — pdfplumber | +22 MB | +8 |
| C. (배제) scikit-learn TF-IDF — numpy·scipy 동반 | +56 MB | +7 |

여기에 얹히는 것: 프론트 번들 1~3MB(빌드 전 추정), Python embeddable 런타임 약 15MB, 앱 소스 1MB 미만.

| 배포 시나리오 | 총 크기 |
|---|---:|
| **M0~M3 (HWPX·DOCX 전용)** | **약 25 MB** ← 이메일 첨부 가능 |
| + PDF | 약 45 MB |
| + scikit-learn을 썼다면 | 약 100 MB |

#### 결정 1: scikit-learn을 쓰지 않고 TF-IDF를 직접 구현한다

numpy+scipy+scikit-learn 56MB는 전체의 절반을 넘는데, 우리가 쓰는 건 TF-IDF 코사인 하나뿐이고 대상은 조항 수백~수천 개 규모다. **순수 파이썬 200줄로 충분하고 이 규모에서 성능 차이가 없다.** 용량보다 중요한 이득은 **보안검토에서 심사할 의존성이 7개 줄어드는 것**이다(§12.4).

#### 결정 2: 배포는 "Python embeddable + wheels + 소스" zip 1개

| 방식 | 배포 편의 | 보안검토 통과 | 채택 |
|---|---|---|---|
| **A. Python embeddable + wheels + 소스 zip** | 압축 해제 후 `run.bat` | **쉬움** — 모든 파일 내용 검증 가능 | **○ 채택** |
| B. wheelhouse만 (`pip install --no-index --find-links vendor/`) | 파이썬 사전 설치 필요 | 쉬움 | △ 차선 |
| C. PyInstaller 단일 `.exe` | 가장 편함 | **어려움** | **× 배제** |

**C를 배제하는 이유가 중요하다.** 단일 exe는 편해 보이지만 (1) 미서명 실행파일은 백신·EDR 오탐이 잦고(PyInstaller가 특히 심하다), (2) AppLocker 등 실행 정책에 걸리며, (3) 무엇보다 **심사자가 내용을 검증할 수 없는 블랙박스**다. 금융권에서 미서명 exe 반입은 사실상 통과되지 않는다. 코드서명 인증서를 구매할 계획이 없다면 선택지가 아니다.

A는 반대로 모든 파일이 열어볼 수 있는 상태로 들어간다. 심사자가 wheel을 풀고 소스를 읽을 수 있다는 점이 통과에 유리하게 작용한다.

#### 빌드 시 유의사항

- 플랫폼별 wheel이 다르므로 **대상 OS·파이썬 버전을 고정**해서 받는다: `pip download --only-binary=:all: --platform win_amd64 --python-version 311` (Win10/11 공통, §12.1 상단 참조)
- 검토 PC에 Python이 없다는 게 확정이므로 **Python embeddable 배포판 동봉이 선택이 아니라 필수**다 — `run.bat`이 동봉된 embeddable로 바로 뜨게 만든다 (사용자가 별도로 아무것도 설치하지 않음)
- OCR을 쓴다면 tesseract 바이너리 + `kor.traineddata` 도 같은 패키지에 포함
- 빌드 스크립트가 §12.4의 제출물 세트를 **자동 생성**하게 만든다

### 12.2 프론트: CDN 참조 0개

빌드 산출물을 레포에 커밋하는 것(§6)만으로는 부족하다. **Google Fonts, unpkg/jsDelivr, CDN 아이콘셋이 하나라도 남아 있으면 폐쇄망에서 화면이 깨진다.** 개발 중 무심코 들어가기 쉬우므로 CI 체크로 막는다.

```
빌드 산출물에서 http(s):// 외부 호스트 참조를 grep → 발견 시 빌드 실패
```

웹폰트도 번들에 포함하거나, 아예 시스템 폰트 스택만 쓴다.

> **현재 프로토타입은 이 원칙을 지키지 못한다.** hwpx·docx 판독과 docx 생성에 쓰는
> JSZip을 cdnjs에서 받고 있다(아티팩트는 CSP상 CDN만 허용되기 때문). **사내 배포판에서는
> JSZip을 번들에 포함해야 한다** — §12.1의 오프라인 패키지에 함께 넣을 항목.
> 미로드 시 "압축 해제 모듈을 불러오지 못했습니다" 안내는 이미 넣어뒀다.

### 12.3 온디바이스 LLM(Chrome Prompt API) 검토 결과 — **보류**

Chrome 148(2026 Q2)부터 Prompt API가 웹페이지용으로 stable이 되어, 확장 없이 로컬 웹앱이 Gemini Nano를 직접 호출할 수 있다. 형태상 diffcheck에 맞아 검토했으나 **현 시점 채택하지 않는다.**

| 사유 | 내용 | 성격 |
|---|---|---|
| **한국어 미지원** | 공식 문서상 지원 언어는 `en·ja·es·de·fr`. 한국어 없음 | **결정타** |
| 부트스트랩에 네트워크 필요 | 모델(2.7~4GB)이 최초 사용 시 다운로드됨. 추론만 오프라인이고 최초 1회는 온라인 필요 → 폐쇄망에서 영원히 안 받아짐 | 구조적 |
| 하드웨어 문턱 | 여유 디스크 22GB + (VRAM 4GB 초과 또는 RAM 16GB·4코어) | 환경 의존 |
| 조직 정책 | `GenAiDefaultSettings` 로 생성형 AI 기능 조직 단위 차단 가능. 금융권은 꺼두는 경우가 많음 | 환경 의존 |
| 모델 체급 | Nano는 소형 모델. `"하여야 한다"→"할 수 있다"` 의 법적 함의 판단은 무리 | 품질 |

특히 하드웨어·정책 조건은 **PC마다 결과가 달라진다**는 뜻이고, 검토 도구에서 사람마다 출력이 다른 것은 그 자체로 결함이다.

**그래서 지금 하는 것**: `llm/adapter.py` 에 얇은 인터페이스만 정의하고 기본 구현을 no-op으로 둔다. 나중에 Chrome Prompt API든 로컬 Ollama든 사내 API든 갈아끼울 수 있다. 지금 비용은 인터페이스 하나뿐이고, 어댑터 없이 만들었다가 나중에 붙이면 코드 곳곳을 뜯어야 한다.

> 참고: 파일 **추출**은 별개 문제이고 이미 해결됐다. 아티팩트 런타임의 `downloads` 능력으로
> 뷰어에게 파일을 건넬 수 있음을 확인했다(확장자 허용 목록에 `docx` 포함). 로컬 실행 시에는
> 일반 다운로드로 폴백한다.

**재검토 트리거**: Prompt API 지원 언어에 `"ko"` 가 추가되는 시점. 그때 위 표의 나머지 4개 조건을 다시 본다.

**애초에 코어는 LLM을 쓰면 안 된다.** 조항 정렬·diff·대비표 생성은 같은 입력에 같은 출력이 나와야 신뢰를 얻는다. LLM은 S4의 "수정 사유 초안 문장 뽑기" 같은 보조 역할에 한정한다. 따라서 이 보류 결정으로 **M0~M3 로드맵은 바뀌지 않는다.**

참고 출처:
- https://developer.chrome.com/docs/ai/prompt-api (지원 언어·하드웨어 요건·모델 다운로드 동작)
- Chrome 148 Prompt API stable 전환 소식
- Chrome `GenAiDefaultSettings` 엔터프라이즈 정책

### 12.4 사내 보안검토 대응

#### 유리한 점 (설계가 이미 이렇게 되어 있다)

- **외부 통신 0건** — 네트워크 명세서에 "없음"으로 적을 수 있는 것이 가장 강력한 논거다
- 127.0.0.1 전용 바인딩, 외부 노출 옵션 자체를 제공하지 않음 (§6.1)
- 데이터가 로컬 파일 밖으로 나가지 않음, 개인정보 수집 없음
- 의존성 전부 널리 쓰이는 오픈소스이고 소스가 공개되어 검증 가능

#### 라이선스 — 사전 확인 결과

| 패키지 | 라이선스 | 판정 |
|---|---|---|
| fastapi, python-docx, pdfplumber | MIT | ○ |
| lxml | BSD-3-Clause | ○ |
| uvicorn, jinja2 | BSD 계열 | ○ |
| **PyMuPDF** | **AGPL-3.0 or Artifex Commercial** | **× 배제** (§5.2) |

AGPL은 사내 전용 도구라 실제 배포 의무가 발생할 여지가 낮더라도, **심사자가 AGPL을 보면 검토가 길어지고 최악의 경우 반려된다.** MIT 대안이 있으므로 논쟁 자체를 만들지 않는다.

#### 걸릴 만한 점과 대응

1. **로컬 웹서버가 포트를 리슨한다** ← 의외의 복병.
   사내 EDR이 "비인가 서버 프로세스"로 탐지할 수 있다. 127.0.0.1 바인딩이라 실제 노출은 없지만 **심사에서 반드시 설명해야 하는 항목**이다.
   대응: 고정 고포트 + localhost 바인딩을 문서에 명시하고, 필요 시 예외 등록을 함께 신청한다.
2. **자료 반입 심사** — SHA-256 해시 목록 + 백신 스캔 결과를 동봉한다.
3. **취약점(CVE)** — `pip-audit` 리포트를 첨부한다. 의존성이 18개뿐이라 관리 가능한 규모다.

#### 제출물 세트 (빌드 스크립트가 자동 생성)

검토 요청 시 아래를 한 번에 제출하면 심사가 훨씬 빨리 끝난다.

- [ ] SBOM (CycloneDX 형식)
- [ ] 의존성 라이선스 목록 (패키지·버전·라이선스·출처 URL)
- [ ] `pip-audit` 취약점 스캔 결과
- [ ] **네트워크 동작 명세** — 외부 통신 없음, 리슨 포트/바인딩 주소 명시
- [ ] 데이터 처리 명세 — 입력 파일 경로, 산출물 경로, 로컬 파일 외 저장 없음, 개인정보 미수집
- [ ] 전체 파일 SHA-256 해시 목록
- [ ] 백신 스캔 결과
