# diffcheck — 정비사업 계약서 검토용 대조 도구 (설계 초안)

> 상태: **초안 (draft)** — 구현 전 합의용 문서. 코드는 아직 없음.
> 작성 기준일: 2026-09-03

---

## 1. 무엇을 만드는가

신탁사(발주처) 입장에서 정비사업 도급계약서를 검토할 때, **두 개(이상)의 계약서를 조항 단위로 대조**하고, 그 결과를 **전/후 대비표 Word 문서로 내보내는** 로컬 웹앱.

기존 `jeongbi-contract-review` 스킬이 "무엇을 어떻게 고칠지"를 판단하는 도구라면, diffcheck은 **"실제로 무엇이 달라졌는지"를 놓치지 않고 잡아내는** 도구다. 역할이 다르고 상호 보완적이다.

| | jeongbi-contract-review 스킬 | diffcheck |
|---|---|---|
| 성격 | 판단·법리 검토 (LLM) | 기계적 대조 (결정론) |
| 입력 | 계약서 1건 + 사업조건 | 계약서 2건 이상 |
| 강점 | 수정안 도출, 법리 근거 | 누락 없는 전수 비교 |
| 약점 | 조항 누락·순서 변경을 놓칠 수 있음 | 무엇이 위험한지 스스로 판단 못함 |

**핵심 사용 시나리오**: 시공사가 500페이지짜리 수정본을 보내왔을 때, 사람이 눈으로 훑어서 "몰래 바뀐 한 줄"을 찾는 일을 없앤다.

## 2. 지원할 비교 모드 (4종)

확정된 4개 축. 엔진은 하나이고, 모드는 **정렬 기준과 라벨링만 다르다**.

| 모드 | 기준(좌) | 대상(우) | 목적 | 우선순위 |
|---|---|---|---|---|
| **A. 원본 vs 우리 수정안** | 접수 원본 | 검토 수정안 | 산출물 2(전/후 대비표) 자동 생성 | ★ 1순위 |
| **B. 표준계약서 vs 시공사 제출본** | 권역 표준계약서 | 시공사 제출본 | 독소조항·무단 변경 탐지 | ★ 1순위 |
| **C. 협상 라운드 간 버전 비교** | N차본 | N+1차본 | 회차별 조항 이력 추적 | 2순위 |
| **D. 과거 사업 계약서 간 비교** | 과거 현장 계약서 | 금번 계약서 | 우리 표준문구 일관성 점검 | 3순위 |

모드 C는 2건 비교의 반복이 아니라 **N-way 타임라인**이 되어야 실용적이다(제24조가 1차→2차→3차에서 어떻게 움직였는지 한 줄로 보기). 초기엔 2건 비교를 반복하는 방식으로 두고, M4에서 타임라인 뷰를 얹는다.

모드 D는 비교라기보다 **문구 라이브러리 조회**에 가깝다. "우리가 쓰는 물가변동 조항 표준문구"를 축적해두고 신규 계약서가 그것과 얼마나 벗어났는지 보는 것. 별도 저장소(문구 DB)가 필요하므로 마지막에 붙인다.

## 3. 진짜 어려운 부분은 diff가 아니라 정렬이다

이 프로젝트의 성패는 여기서 갈린다. 먼저 짚고 간다.

계약서 비교를 `diff a.txt b.txt` 로 하면 반드시 실패한다. 이유:

1. **조 번호가 밀린다.** 시공사가 제24조의2를 신설하면 그 아래 모든 조 번호가 한 칸씩 밀린다. 번호로 맞추면 25조부터 전부 "변경됨"으로 나온다 → 실제 변경 3건이 40건으로 보이고, 사람은 리포트를 안 보게 된다.
2. **조항 순서가 바뀐다.** 장(章) 구성을 재배치하는 경우가 있다.
3. **조사·어미 변화가 노이즈다.** "공사비를 조정한다" vs "공사비는 조정하기로 한다" — 문자 diff는 이걸 전면 재작성으로 표시한다.
4. **표(表)가 많다.** 공사비 내역, 마감재 사양표. 표는 문장이 아니라 **셀 단위**로 비교해야 한다.
5. **줄바꿈·공백이 포맷마다 다르다.** HWPX와 PDF에서 같은 문장이 다르게 떨어진다.

그래서 파이프라인을 **파싱 → 정규화 → 정렬 → diff** 4단으로 분리하고, 정렬 단계를 독립 모듈로 둔다.

### 3.1 조항 정렬 알고리즘 (제안)

```
1단계  조 번호 정확 매칭          — 번호+제목이 모두 같으면 확정 앵커
2단계  앵커 사이 구간을 순서보존 정렬 (Needleman-Wunsch)
        점수 = 0.4·제목유사도 + 0.5·본문유사도 + 0.1·번호근접도
        본문유사도 = 어절 TF-IDF 코사인 (외부 API 없이 로컬 계산)
3단계  임계치 미만 → 신설(우측 단독) / 삭제(좌측 단독)로 확정
4단계  사람이 화면에서 매칭을 수정할 수 있어야 한다  ← 필수
```

4단계를 빼면 안 된다. 자동 정렬은 90%만 맞고, 나머지 10%를 사람이 못 고치면 도구를 신뢰하지 않게 된다. **정렬 결과 검수 화면이 이 앱의 핵심 UX다.**

### 3.2 diff 3단 계층

정렬된 조 쌍 안에서만 diff를 돌린다.

```
조(Article) 단위   → 신설 / 삭제 / 변경 / 동일
  └ 항(Paragraph)  → 항 단위 정렬 후 diff
      └ 문장 단위   → 어절(띄어쓰기) 토큰 diff
```

한글 노이즈 억제: 어절 토큰 diff를 기본으로 하되, **"조사만 다른 어절"은 경미(minor) 변경으로 별도 표시**한다. 형태소 분석기(kiwi 등) 도입은 선택지로 남기되, 의존성이 무거우므로 M1에서는 조사 목록 기반 휴리스틱으로 처리하고 효과를 본 뒤 결정.

## 4. 공통 중간표현 (CDM)

포맷이 4종이므로, **모든 파서는 동일한 JSON 구조를 뱉는다.** 정렬·diff·내보내기는 원본 포맷을 전혀 모른다. 이 경계가 설계의 중심이다.

```jsonc
{
  "meta": {
    "source_file": "도급계약서_시공사제출본.hwpx",
    "format": "hwpx",
    "parsed_at": "2026-09-03T10:00:00+09:00",
    "confidence": 0.95        // PDF/HWP는 낮게 나옴 → UI에 경고 표시
  },
  "nodes": [
    {
      "id": "art-24",
      "type": "article",       // chapter | article | paragraph | item | subitem | table
      "number": "제24조",
      "number_norm": 24,       // 정렬용 정규화 번호
      "title": "물가변동으로 인한 계약금액의 조정",
      "text": "...",           // 하위 노드 텍스트 합본 (정렬 유사도 계산용)
      "children": [ /* 항 */ ],
      "source_span": { "section": 0, "para_start": 412, "para_end": 431 }
    },
    {
      "id": "tbl-3",
      "type": "table",
      "caption": "마감재 사양표",
      "cells": [["구분","사양","비고"], ["바닥","강마루","..."]]
    }
  ]
}
```

`source_span`을 반드시 유지한다. "원본 몇 페이지에 있던 조항인가"를 UI와 대비표에서 되짚어야 하기 때문.

## 5. 포맷별 파싱 전략과 난이도

| 포맷 | 방식 | 난이도 | 구조 복원 신뢰도 | 비고 |
|---|---|---|---|---|
| **HWPX** | ZIP 해제 → `Contents/section*.xml` (OWPML) 파싱 | 중 | 높음 | 스킬의 `extract_hwpx.py`를 출발점으로 확장. 표·스타일 정보까지 살릴 것 |
| **DOCX** | `python-docx` | 하 | 높음 | 가장 안정적. 내보내기도 이 포맷 |
| **HWP (구버전)** | CFB 컨테이너 + 압축 레코드 스트림 | **상** | 중 | 파이썬 생태계가 빈약. 아래 별도 논의 |
| **PDF** | `PyMuPDF`/`pdfplumber`, 텍스트 레이어 없으면 OCR | **상** | 낮음 | 조항 구조를 좌표·폰트크기로 추정해야 함 |

### 5.1 HWP 구버전 — 권고안

구버전 `.hwp` 바이너리 파서는 유지보수 부담 대비 효용이 낮다. 3단 폴백을 제안한다:

1. **기본 방침**: 사용자에게 "한글에서 `.hwpx`로 다시 저장" 안내 (실무상 대부분 가능)
2. **자동 변환 시도**: 한글이 설치된 PC라면 변환 스크립트 연동 (Windows COM 자동화)
3. **최후**: best-effort 텍스트 추출 후 `confidence: 0.5` 로 표시하고, 정렬 검수 화면을 강제로 거치게 함

이 결정은 되돌릴 수 있으니, 우선 1번만 구현하고 실제로 구버전 파일이 얼마나 들어오는지 보고 판단하자.

### 5.2 PDF — 권고안

PDF는 **비교의 기준(좌)으로만 쓰고, 대비표 생성의 대상(우)으로는 쓰지 않는다**고 선을 긋는 편이 낫다. 구조 복원이 불완전한 문서를 근거로 "제24조 제3항이 이렇게 바뀌었다"고 문서화하면 신뢰 사고가 난다. OCR은 M4 이후.

## 6. 아키텍처

```
┌─────────────────── 브라우저 (localhost:8765) ───────────────────┐
│  업로드 → 정렬 검수 → 좌우 대조 뷰 → 사유 입력 → 내보내기         │
└───────────────────────────┬─────────────────────────────────────┘
                            │ HTTP (로컬 전용, 127.0.0.1 바인딩)
┌───────────────────────────┴─────────────────────────────────────┐
│  FastAPI 백엔드                                                  │
│    parsers/   hwpx.py  docx.py  hwp.py  pdf.py    → CDM          │
│    align/     anchor.py  similarity.py  nw.py                    │
│    diff/      article.py  sentence.py  token.py  table.py        │
│    rules/     risk_tags.py      ← 정비사업 도메인 룰             │
│    export/    comparison_docx.py                ← 산출물 2 규격  │
│    store/     세션·프로젝트 SQLite (로컬 파일)                    │
└─────────────────────────────────────────────────────────────────┘
```

**스택 선택 근거**
- 백엔드 Python: hwpx/docx/pdf 파싱, docx 생성, 유사도 계산이 전부 파이썬 생태계에 있음. 스킬의 기존 스크립트와도 이어짐.
- 프론트 React + Vite: 좌우 스크롤 동기화, 가상 스크롤(1000조항), 인라인 편집이 필요해서 vanilla로는 금방 한계. 다만 **빌드 산출물을 레포에 커밋**해서 `pip install` 만으로 실행되게 한다(검토자 PC에 Node 요구 X).
- 실행: `diffcheck serve` → 브라우저 자동 오픈.

### 6.1 보안 원칙 (타협 없음)

계약서는 전량 대외비다.

- 서버는 **127.0.0.1 에만 바인딩**. 외부 노출 옵션 자체를 제공하지 않는다.
- **외부 네트워크 호출 없음**이 기본값. 유사도 계산도 로컬 TF-IDF로 하고 임베딩 API를 쓰지 않는다.
- 업로드 파일은 사용자가 지정한 작업 폴더에만 저장. 임시 디렉터리에 잔재를 남기지 않는다.
- LLM 연동(변경 요약 자동 생성 등)은 **명시적 opt-in**으로만. 기본 꺼짐, 켤 때 "본문이 외부로 전송됨" 경고.

## 7. 화면 설계

**S1. 업로드 & 모드 선택**
좌/우 파일 드롭 + 비교 모드(A~D) 선택. 파싱 결과 요약(조 수, 표 수, 신뢰도) 즉시 표시.

**S2. 정렬 검수** ← 핵심
자동 매칭 결과를 3열(좌 조항 / 매칭선 / 우 조항)로 보여주고, 낮은 신뢰도 매칭을 상단에 모아준다. 드래그로 매칭 수정, 매칭 해제, 수동 연결. 여기서 확정해야 다음으로 넘어간다.

**S3. 대조 뷰**
좌우 스크롤 동기화 + 어절 단위 하이라이트. 필터: `변경 / 신설 / 삭제 / 경미(조사만) / 동일(기본 숨김)`. 좌측 미니맵에 변경 지점을 색 띠로 표시(전체 분량 감각).

**S4. 검토 코멘트**
각 변경 건마다 `수정 사유 / 법리근거 / 우선순위(Must·Should·Nice)` 입력. 대비표의 마지막 컬럼이 여기서 채워진다. 자주 쓰는 사유는 스니펫으로 저장·재사용.

**S5. 내보내기**
선택한 건만 골라서 대비표 생성. 미리보기 후 `.docx` 저장.

## 8. 도메인 룰: 위험도 자동 태깅

범용 diff 도구와 diffcheck을 가르는 지점. 변경된 조항에 키워드·패턴 룰을 걸어 자동으로 등급을 매긴다.

| 등급 | 트리거 예시 |
|---|---|
| **★ 최우선** | 물가변동, 계약금액 조정, 공사비 검증, 정비사업지원기구, 착공, 사업시행계획인가 |
| ● 중요 | 계약보증금, 하자담보, 손해배상 예정, 지체상금, 품질사양서, 동등품 |
| ○ 확인 | 통지, 기한, 협의, 준용 |

추가로 **위험 패턴 탐지**(문구 변화의 의미를 잡는 룰):
- 의무 → 임의: `"하여야 한다" → "할 수 있다"`
- 주체 전환: `"시공사는" → "발주처는"` (책임 이전)
- 한정어 삽입: `"중대한", "불가피한", "상호 협의하여"` 신규 삽입
- 수치 변경: `5‰/15% → 10‰/20%` 같은 임계치 완화 (숫자 토큰 비교)
- 삭제된 조항 중 강행규정 관련(도시정비법 §29조의2 등)

이 룰들은 `rules/*.yaml` 로 데이터화해서 코드 수정 없이 늘릴 수 있게 한다.

## 9. 내보내기 — 산출물 2 규격 준수

스킬 `assets/template_comparison.md` 의 규격을 그대로 따른다. 이걸 지켜야 기존 검토 문서와 섞어 쓸 수 있다.

- A4 **가로(landscape)**
- 컬럼: `No.(A-1 형식) | 조항 | 【전】원본 | 【후】수정 제안 | 수정 사유/법리근거`
- 색상: 헤더 `#1F3A5F`(흰 글씨) / 원본셀 `#FFF5F5`(강조 `#C00000`) / 수정안셀 `#F0F8E8`(강조 `#0070C0`) / 사유셀 `#FFFEF0`
- 카테고리 A~D 끝마다 "처리 핵심" 강조박스
- 셀 안에서 변경된 어절만 굵게/색으로 강조 (diff 결과를 그대로 서식에 반영 — 손으로 만들 때 가장 귀찮은 부분이 자동화됨)

부가 산출물로 `changes.json`(전체 변경 원장)과 `summary.csv`를 함께 뱉는다. 후자는 협상 회차별 진행 관리에 쓴다.

## 10. 단계별 로드맵

| 단계 | 범위 | 완료 기준 | 예상 |
|---|---|---|---|
| **M0** | CDM 스키마 확정 + HWPX·DOCX 파서 + `diffcheck parse` CLI | 실제 계약서 1건이 조/항/호로 정확히 쪼개져 JSON으로 나옴 | 1주 |
| **M1** | 정렬 엔진 + 3단 diff + 콘솔 리포트 | 조 번호가 밀린 실제 케이스에서 오탐 없이 매칭됨 | 1.5주 |
| **M2** | 웹 UI (S1~S3) + 정렬 수동 보정 | 검토자가 브라우저에서 전 과정 수행 가능 | 2주 |
| **M3** | S4·S5 + docx 대비표 내보내기 | 손으로 만든 대비표와 구분이 안 될 품질 | 1주 |
| **M4+** | 위험도 룰 / HWP·PDF / 모드 C 타임라인 / 모드 D 문구DB | — | 이후 |

**M0~M1이 전체의 성패**다. 여기서 실제 계약서로 정렬 정확도를 못 뽑으면 UI를 아무리 잘 만들어도 안 쓰게 된다. M1 끝에서 반드시 실물 계약서 3건으로 검증하고 진행 여부를 재판단한다.

## 11. 아직 결정 안 한 것

1. **구버전 HWP를 정식 지원할 것인가** — 실제 유입 비율을 보고 M4에서 결정 (§5.1)
2. **형태소 분석기 도입** — 조사 휴리스틱으로 충분한지 M1에서 측정 후 판단
3. **LLM 연동 범위** — 변경 요약문 자동 초안 정도는 유용하나, 대외비 전송 문제. opt-in 로컬 모델도 선택지
4. **모드 D 문구 DB 스키마** — 과거 계약서를 몇 건이나 적재할지, 조항 단위 색인 방식
5. **다중 사용자** — 현재 설계는 1인 로컬 전용. 팀 공유가 필요해지면 아키텍처가 달라짐 (지금은 하지 않는 쪽 권장)
6. **jeongbi 스킬과의 연동 방향** — diffcheck의 `changes.json` 을 스킬이 읽어 검토의견서를 쓰는 구조가 자연스러움. 인터페이스는 M3 이후 확정

## 12. 다음 액션
