# 실험: 문서 간 조항 대조가 어휘 유사도로 가능한가

> **결과: 불가능하다.** 이 실험은 잘못된 구현을 막기 위해 남긴다.
> 관련 설계 결론은 `docs/DESIGN-DRAFT.md` §2.2.

```bash
python3 match_test.py
```

## 왜 해봤나

신탁계약서는 다른 계약서들의 **허브**다. 본문에 이런 조항이 박혀 있다:

- **제11조(공사도급계약)** — "위탁자가 이미 체결한 공사도급계약이 있는 경우 **이를 승계할 수 있다**",
  ③항에 시공사 **책임준공의무**
- **제12조(설계·감리 등 용역계약)** — 마찬가지로 승계 조항
- **제13조(자금조달)** — 위탁자 조달 원칙, 미달 시 시공사 **신용보강·자금지원**

그리고 실무에서 이 문서들 사이의 정합성을 **실제로 대조한다**(사용자 확인). 예: 신탁계약서
제11조③이 정한 책임준공의무가 실제 도급계약서에 같은 강도로 들어가 있는지.

그렇다면 이미 만든 정렬 엔진(NW)을 문서 간 대조에 재사용할 수 있는지가 첫 질문이었다.

## 결과

신탁계약서 35조 각각에 대해 도급계약서 43조 중 최유사 조를 찾았다.

```
★ 0.46  신탁 제2조(용어의 정의)        ↔ 도급 제2조(정의)             맞지만 무의미
★ 0.44  신탁 제20조(신탁건물 하자담보)  ↔ 도급 제31조(하자담보)         맞음
★ 0.38  신탁 제34조(관계법령의 준수)    ↔ 도급 제40조(법령의 준수)      맞음
  0.22  신탁 제11조(공사도급계약)      ↔ 도급 제32조(건설공사의 하도급) 헛매칭
  0.22  신탁 제9조(수익권의 양도)      ↔ 도급 제38조(채권양도)         헛매칭

0.25 이상: 3건 / 35건
```

이 수치는 문자 n-gram 유사도(`timemachine/src/app.js` 와 동일)로 잰 것이다. **처음엔 어절
코사인으로 재서 2건이었고**, `관계법령의 준수`↔`법령의 준수`가 0.17에 묻혀 있었다.
그 결과가 정렬 엔진의 유사도 함수를 n-gram으로 바꾸게 만든 출발점이다(`../timemachine/README.md`).

n-gram이 정답 2건(하자담보·법령준수)을 건져냈지만 **3/35는 여전히 쓸 수 있는 수준이 아니고,
헛매칭도 그대로 남는다.** 결론은 바뀌지 않는다.

## 세 가지 구조적 이유

1. **같은 사항을 다른 어휘로 쓴다.** 신탁계약서는 `수탁자/위탁자`, 도급계약서는 `도급인/수급인`.
   같은 준공 얘기를 해도 어휘가 겹치지 않는다.
2. **길이 편향.** 길고 어휘가 다양한 조항이 여러 신탁 조항의 "최유사"로 반복 등장한다.
   어절 코사인일 때는 도급 제22조(원자재 가격변동) 하나가 최유사 12건 중 4번을 차지했다.
3. **순서 보존이 성립하지 않는다.** 대응 조항이 앞에 있을 수도 뒤에 있을 수도 있으므로
   NW를 쓸 수 없다. 같은 문서의 두 버전을 비교할 때와 근본적으로 다르다.

1번과 2번은 유사도 함수를 바꿔 완화할 수 있지만(문자 n-gram으로 3건까지 올랐다),
**3번은 함수로 해결되지 않는다.** 그리고 `수탁자`↔`도급인` 같은 어휘 체계 차이는
형태소 분석을 넣어도 남는다.

## 그래서 어떻게 가야 하나

조항을 짝짓지 말고 **점검 항목에서 출발한다.** 항목을 룰로 정의하고, 각 문서에서 키워드로
해당 조항을 찾아 **값을 뽑아 대조**한다.

```yaml
# rules/cross-check.yaml
- id: 책임준공
  문서: [신탁계약서, 도급계약서, 대출약정서]
  키워드: [책임준공, 준공인가, 사용승인, 준공기한]
  추출: [기한, 예외사유]
```

결과는 diff 그리드가 아니라 **정합성 매트릭스**다.

```
항목        신탁계약서      도급계약서        대출약정서
책임준공    제11조③        제10조            제7조(EOD)
            불가항력만 예외  민원 시 연장 가능  ⚠ 예외사유 불일치
```

**어떤 항목을 점검할지는 알고리즘이 발견하지 못한다.** 도메인 지식이므로 사람이 룰에 넣어야
하고, 한 번 넣으면 모든 사업에 재사용된다.

## 데이터

금감원 신고 약관은 각 사가 홈페이지에 공시하므로 실물을 받을 수 있다. 도급계약서 때와 달리
**합성 없이 실물로 검증 가능**하다.

| 파일 | 출처 | 분량 |
|---|---|---|
| `ktrust_land.pdf` | 한국토지신탁 「토지신탁계약서(관리형)」 | 25p · 35조 · 표 2개 |
| `wooriat_dambo.pdf` | 우리자산신탁 「담보신탁계약서(약관)」 2024.06.05 개정 | 14p · 28조 · 표 4개 |

`.txt`는 pdfplumber로 추출한 것이다.

**표가 적다는 것도 확인됐다** — 25페이지에 2개, 14페이지에 4개. 신탁계약서는 거의 순수 조문이라
표 비교 기능의 우선순위를 내려도 된다(도급계약서 전용 기능으로 강등).

## 이 실험이 낳은 것

모드 E(본문 ↔ 특약 override)는 이 데이터의 본문을 써서 프로토타입으로 만들었다 —
`../timemachine/` 참조. **특약은 합성이다.** 공개 약관의 `[별첨5] 신탁특약`이 빈 템플릿이라
실물을 구할 수 없었다(금감원 신고 대상은 표준약관이고, 특약은 사업장별 비공개 문서다).

특약은 본문과 비슷한 분량이고 제35조에 따라 **본문을 우선(override)** 하므로 신탁계약서
검토의 본체다. **실물 특약 샘플 1건이 확보되면 즉시 재검증할 것.**
