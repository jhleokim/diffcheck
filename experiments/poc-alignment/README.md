# POC: 조항 정렬(alignment) 실현가능성 검증

> **상태: 1회성 실험, 프로덕션 코드 아님.** M0 시작 시 이 스크립트는 버리고 정식 구현으로 교체한다.
> 목적은 설계 초안(`docs/DESIGN-DRAFT.md` §3.1)의 핵심 가설 — "번호가 밀려도 정렬이 된다" — 을
> **실제 정부 공개 계약서 원문**으로 최소 검증하는 것.

## 왜 이 파일들이 여기 있는가

회사 실제 계약서 샘플을 구하기 전, 웹에서 접근 가능한 **공공기관 공개 표준계약서**로
먼저 파이프라인의 가장 위험한 가정(조항 정렬)을 찔러봤다. 아래 두 파일 모두
정부/지자체가 공중 참고·다운로드용으로 배포한 표준양식이라 대외비·저작권 문제가 없다.

| 파일 | 출처 | 성격 | 용도 |
|---|---|---|---|
| `minganbuild_standard_contract.pdf` | [국가법령정보센터](https://law.go.kr) 붙임, 건설산업기본법 시행령 관련 「민간건설공사 표준도급계약서」 | 실제 정부 공개 PDF, 17페이지, 조 43개 | 정렬 POC의 "원본" 소스 |
| `ydp_construction_standard.hwp` | [영등포구청](https://www.ydp.go.kr) 공사도급표준계약서 | 실제 구버전 HWP 5.0 바이너리 | §5.1 "구버전 HWP" 난제의 실물 표본 (아직 파싱 안 함) |

**국토교통부가 2024년 배포한 「정비사업 표준공사계약서」(진짜 타깃 문서)는 이 세션 환경에서
molit.go.kr 접속 자체가 막혀 못 받았다** (curl은 connection reset, WebFetch는 리다이렉트 루프 —
정부기관 사이트의 흔한 자동화 클라이언트 차단 패턴). 브라우저가 있는 환경에서 재시도하거나,
회사 자료로 대체하면 된다. 링크만 남겨둔다:
- https://www.molit.go.kr/USR/policyData/m_34681/dtl.jsp?id=4744

## 무엇을 검증했나

`minganbuild_standard_contract.pdf`에서 실제 조 43개를 추출한 뒤(`articles_before.tsv`),
**인위적으로 "협상 후 수정안"을 합성**해서 정렬 알고리즘 프로토타입(`poc_align.py`)에 넣었다.
주입한 변형은 실제 협상 라운드에서 흔한 4가지 패턴:

1. 제10조 뒤에 신설조항 삽입 → **11조부터 전부 번호가 1씩 밀림** (§3에서 지목한 최악 케이스)
2. 원 제25조를 통째로 삭제
3. 원 제15조·제30조 본문에 조사만 바꾼 노이즈 삽입 (`"한다"→"하기로 한다"` 등)
4. 원 제18조는 **제목까지** 살짝 바뀜 (`"부적합한 공사"→"부적합한 공사 등"`) — 번호+제목
   완전일치 앵커만으론 못 잡는, 본문 유사도가 필요한 케이스

정렬 로직은 설계 초안 §3.1 그대로: 1단계 번호+제목 완전일치 앵커, 2단계 나머지는
`0.4·제목유사도 + 0.5·본문유사도 + 0.1·번호근접도` 최고점 매칭. 유사도는 §12.1 결정대로
**scikit-learn 없이 순수 파이썬 단어빈도 코사인**으로 구현.

## 결과 (`poc_align_output.txt` 전체 로그)

- 번호가 밀린 33개 조 — **전부 정확히 재정렬** (오탐 0건)
- 신설조항 1건 — "신설후보"로 정확히 분류, 다른 조와 오매칭 없음
- 삭제조항 1건 — "삭제후보"로 정확히 분류
- 제목이 바뀐 제18조 — 앵커 매칭은 실패했지만 본문 유사도로 정확히 잡힘 (앵커 단독 설계였다면 놓쳤을 케이스)
- 조사만 바뀐 노이즈 2건 — 유사도 0.95로 잘 흡수됨 (문장 재작성으로 오판하지 않음)

**즉 §3의 핵심 가설(번호 정렬 대신 앵커+유사도 정렬을 쓰면 오탐 없이 매칭된다)이 최소 조건에서 성립.**

## 이 결과의 한계 — 과신 금지

- 원본이 실제 신탁사 정비사업 도급계약서가 아니라 **일반 민간건설공사 표준계약서**다. 조 구조는
  유사하지만 정비사업 특유 조항(공사비 검증, 정비사업지원기구 등)은 여기 없다.
- "수정안"이 **인위적으로 합성**한 것이지 실제 시공사 협상 redline이 아니다. 실전에서는
  문장을 통째로 재작성하는 경우가 훨씬 많을 수 있고, 그 경우 본문 코사인 유사도가
  이번처럼 0.95까지 높게 나오지 않을 수 있다.
- 43개 조 규모에서만 검증했다. 정비사업 계약서는 이보다 조가 많고 표(表)도 낀다 —
  표 처리는 여기서 아예 테스트 안 됨.

**결론: 이 POC는 "가설이 말이 안 되는 건 아니다"를 확인한 것이지, M1 완료 기준
("실물 계약서 3건 검증")을 대체하지 않는다.** 회사 실제 샘플이 오면 반드시 재검증.

## 재현 방법

```bash
python3 poc_align.py
```

의존성 없음(표준 라이브러리만 사용). `articles_before.tsv`를 읽어 정렬 결과를 stdout에 출력한다.
