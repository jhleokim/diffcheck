# 프로토타입: 조항 대조 도구 (타임머신 + 특약 override)

> **상태: 프로토타입.** M0/M2 착수 시 정식 구현으로 교체한다. 다만 아래 §정렬 엔진과
> §파일 판독은 **검증을 마친 로직이므로 그대로 이식할 것.**
> 존재 이유는 `docs/DESIGN-DRAFT.md` §7 화면 설계를 상상이 아니라 실물로 확정하는 것.

**`timemachine.html`은 빌드해둔 결과물이다. 그냥 브라우저로 열면 된다** — 검토 PC에는
Python이 없으므로(§12.1) 빌드 과정 없이 바로 쓸 수 있어야 한다. 단, hwpx·docx 판독과
docx 추출은 JSZip을 cdnjs에서 받으므로 인터넷이 필요하다(아래 CDN 의존 주의 참조).

소스를 고쳤을 때만 다시 빌드한다:

```bash
python3 gen_rounds.py    # articles_full.tsv          → versions.json (도급 4회차, 합성)
python3 gen_sintak.py    # ../cross-document/*.txt    → sintak.json   (신탁 본문+특약)
python3 build_sets.py    # 위 둘                       → sets.json
python3 build.py         # src/ + sets.json           → timemachine.html
```

## 두 개의 문서 세트, 두 개의 모드

| 세트 | 모드 | 좌 | 우 | 정렬 결과의 의미 |
|---|---|---|---|---|
| 공사도급계약서 | `version` | N차본 | N+1차본 | 변경·신설·삭제 |
| 신탁계약서 | `override` | 본문(실물) | 특약(합성) | **특약이 본문을 대체** |

같은 정렬 엔진이 두 모드를 모두 처리한다. 달라지는 것은 **상태 라벨, 접기 기준, 집계**뿐이다.

| 정렬 status | version 모드 | override 모드 |
|---|---|---|
| same / moved / edited | 동일 · 번호 이동 · 내용 변경 | **특약이 대체** ← 핵심 검토 대상 |
| inserted | 신설 | **본문에 없는 신규 특약** |
| deleted | 삭제 | 특약 없음 (본문 그대로) — **안전한 쪽** |

**접기 기준이 반전된다.** version 모드는 `same` 을 접고, override 모드는 `deleted`(특약이
건드리지 않은 본문 조)를 접는다. override 모드에는 `same` 이 아예 없다 — 특약 문구가
본문과 같을 리 없기 때문이다.

## 정렬 엔진 — 두 번의 부정 결과로 다듬었다

### 1차: 탐욕법은 반드시 실패한다

초판은 §3.1이 지정한 Needleman-Wunsch 대신 탐욕적 매칭(`각 조마다 남은 것 중 최고점을 고름`)
으로 구현했고, 정확도가 **39/42**였다. v1에서 `제25조(기성부분금)`이 삭제되자:

```
제25조(기성부분금)  → 제25조(손해의 부담)   0.30   ← 오매칭 (임계값 턱걸이)
제26조(손해의 부담) → 제26조(부분사용)      0.31   ← 연쇄
제27조(부분사용)   → 제27조(준공검사)      0.32   ← 연쇄
제28조(준공검사)   → 짝 없음 = 삭제로 오판
```

원인 둘: **탐욕법은 전역 최적을 보지 않는다**, 그리고 **번호 근접도 항(`0.1/(1+Δ)`)이
오답을 유도했다** — 삭제로 번호가 밀린 직후에는 "번호가 같으니 맞다"가 정확히 틀린 신호다.

→ **순수 Needleman-Wunsch** (`GAP=0.40`, `FLOOR=0.25`, 번호 항 제거)로 교체. 네 라운드 100%.

### 2차: 어절 토큰화는 override에서 무너진다

모드 E를 붙이자 override 정확도가 **1/21** 이 나왔다. 정답 쌍의 평균 유사도가 0.134였다.

```
관할법원  ↔  관할법원의 특례      유사도 0.000   ← 완벽한 정답 쌍인데 0점
```

원인 셋:

1. **한국어 조사.** 어절 토큰이라 `관할법원` ≠ `관할법원의`. 정답이 0점이 된다.
2. **길이 비대칭.** 본문 평균 415자 vs 특약 평균 82자. 짧은 쪽이 긴 쪽의 어휘를 다 담을 수
   없어 코사인이 구조적으로 낮게 나온다.
3. **어휘 재사용 없음.** 특약은 본문 문구를 반복하지 않고 새로 쓴다.

→ 유사도 함수를 세 가지로 교체했다:

| 바꾼 것 | 이유 |
|---|---|
| 어절 토큰 → **문자 n-gram** (제목 2-gram, 본문 3-gram) | 형태소 분석기 없이 조사 문제 우회 |
| 제목 코사인 → **포함도(containment)** | 길이 비대칭에 강함 |
| **명시 참조 보너스 +0.5** | 특약은 "신탁계약 제11조에도 불구하고"처럼 본문을 직접 인용한다. 가장 확실한 근거 |

측정:

| 유사도 함수 | 정답 쌍 평균 | 0.25 이상 |
|---|---|---|
| 어절 코사인 (구) | 0.134 | 1 / 21 |
| 문자 3-gram 코사인 | 0.249 | 10 / 21 |
| 3-gram + 제목 포함도 | 0.431 | 17 / 21 |
| **+ 명시 참조 보너스 (채택)** | — | **override 17/21** |

**버전 비교는 회귀 없이 100% 유지된다** (42/42, 43/43, 44/44, 43/43). 한 함수로 두 모드를
모두 처리한다.

> 이 결과는 §11 미결정 2번(형태소 분석기)에 부분적인 답을 준다 — **조사 문제는 형태소 분석기
> 없이 문자 n-gram으로 해결된다.** 다만 §2.2의 문서 간 매칭(`수탁자`↔`도급인`)은 여전히 별개 문제다.

### 남은 한계: override는 1:N이다

특약 하나가 본문 여러 조를 건드린다. 예: 「분양가의 결정 및 분양업무」 특약이 본문
제15조(분양 등 처분)와 제16조(분양업무 수행)를 동시에 대체한다. **지금 정렬 엔진은 1:1
매칭만 만들 수 있다.** 실패 4건 중 최소 2건이 이 문제이거나 정답 라벨 자체가 애매한 경우다.

## override 모드에서는 어절 diff를 꺼야 한다

처음엔 켜뒀는데, 매칭된 조가 **전부 빨강/초록으로 칠해져** 읽기가 불가능했다.
특약은 본문을 고친 게 아니라 **다른 문장으로 새로 쓴 것**이라 어절 diff가
"전부 삭제 + 전부 추가"로 본다.

**override 모드에서는 원문을 그대로 보여주고, 거터가 관계만 표시한다** (`→` 대체 / `·` 특약 없음 /
`+` 신규). 상태바의 "추가 N곳·삭제 N곳"도 같은 이유로 숨긴다.

## 파일 판독 — hwpx·docx는 브라우저에서 열린다

둘 다 **ZIP + XML**이라 JSZip만으로 처리된다. 별도 서버·변환기가 필요 없다.

| 형식 | 방법 | 상태 |
|---|---|---|
| `.hwpx` | ZIP → `Contents/section*.xml`(OWPML) → `<hp:t>` 수집, `</hp:p>`에서 줄바꿈 | 지원 |
| `.docx` | ZIP → `word/document.xml` → `<w:t>` 수집, `</w:p>`에서 줄바꿈 | 지원 |
| `.hwp` `.doc` | 구버전 바이너리 | 안내 후 거절 (§5.1 방침) |
| `.pdf` | — | 미지원 (아래) |

**hwpx에서 반드시 주의할 점**: 한글은 글자 서식이 바뀌면 한 문단 안에서도 `<hp:t>` 런이
쪼개진다. 런 단위로 줄을 나누면 `"도급인과 / 수급인은"` 처럼 조문이 끊긴다.
**문단(`</hp:p>`) 기준으로만 줄을 나눌 것.**

검증: 우리 docx 생성기로 만든 파일을 되읽는 **왕복 시험**에서 `제3조의2` 가지번호와
`<건설공사> &` 특수문자까지 정확히 복원됐다. hwpx는 다중 section 병합과 런 병합을 확인했다.

**PDF를 넣지 않은 이유**: pdf.js가 ES 모듈 + 별도 워커를 요구해 이 환경에서 검증할 수 없었다.
검증하지 못한 코드는 넣지 않는다. §5.2도 PDF는 대비표 근거로 쓰지 않기로 이미 정했다.

## docx 생성 — OOXML을 직접 쓴다

cdnjs에 docx 라이브러리가 없어 **JSZip으로 OOXML을 직접 조립**한다. 최소 구조로 충분하다:

```
[Content_Types].xml
_rels/.rels
word/document.xml     ← 본문 + <w:sectPr> (가로 A4: w=16838 h=11906 orient=landscape)
```

산출물 2 규격(§9)의 색상을 `<w:shd w:fill="...">`로 그대로 넣는다 — 헤더 `1F3A5F`,
원본셀 `FFF5F5`, 수정안셀 `F0F8E8`, 사유셀 `FFFEF0`.

검증: `file` 명령이 `Microsoft Word 2007+`로 인식하고, 세 XML 파트 모두 파서를 통과하며
가로 A4 지시가 확인됨. **다만 실제 Word에서의 렌더링은 아직 확인하지 못했다.**

## 데이터의 성격 — 어디까지가 진짜인가

| | 진짜 | 합성 |
|---|---|---|
| 도급계약서 | 43개 조 원문 (국가법령정보센터 공개) | 협상 4회차 |
| 신탁계약서 | **본문 35개 조 원문** (한국토지신탁 공시 약관) | **특약 30개 조** |
| 정렬 결과 | 브라우저에서 실제 계산. 하드코딩 아님 | — |

합성 부분은 실무에서 실제로 쓰이는 수법을 본떴다. 도급은 임계치 없는 물가변동 특례 신설,
손해의 부담 조항 삭제, 원자재 연동 기준 완화, `응하여야 한다`→`응할 수 있다`, 그리고
발주처 검토에서의 되돌림. 특약은 우선수익권 순위·한도, 책임준공기한 명시, 수탁자 면책 범위
확대, 신탁보수 요율, 책임준공 미이행 시 조치 등.

**실물 특약은 사업장별 비공개 문서라 구할 수 없다.** 금감원 신고 대상은 표준약관이고,
공개 약관의 `[별첨5] 신탁특약`은 빈 템플릿이다. **실물 특약 샘플 1건이 확보되면 즉시 재검증할 것.**

## 구현자가 반드시 알아야 할 함정

프로토타입에서 실제로 겪은 것만 적는다.

- **행 인덱스를 `자식위치 / 3`으로 계산하지 말 것.** 접힘 밴드는 그리드 자식을 1개만
  차지해 산술이 깨지고 트래킹이 엉뚱한 조를 가리킨다. 각 셀에 `data-row`를 박을 것.
- 하이픈이 든 id(`hl-nm`)를 암묵적 전역으로 참조하면 렌더 함수가 통째로 죽는다.
- 조문 본문은 클램프 필수. 안 하면 조 하나가 화면 절반을 먹는다.
- 대비표 표는 `table-layout:fixed` + `colgroup` 없이는 컬럼이 한 글자씩 끊긴다.
- **문자열 치환 패치에 assert를 빠뜨리지 말 것.** override 모드에서 우측 셀의 diff를 끄는
  치환이 조용히 실패해, 좌측만 고쳐지고 우측은 초록 범벅인 채로 한 번 넘어갔다.
- **CDN 의존 주의**: 지금 JSZip을 cdnjs에서 받는다. §12.2의 "CDN 참조 0개" 원칙과 충돌하므로
  **사내 배포판에서는 반드시 번들에 포함**해야 한다. 미로드 시 안내 메시지는 넣어뒀다.

## 한계

- 도급계약서는 신탁사 정비사업 계약서가 아니라 일반 민간건설 표준계약서다.
- 신탁 특약은 합성이다. override 정확도 17/21은 **합성 데이터 기준**이라 실물에서는 달라진다.
- 표(表) 처리는 테스트조차 안 됐다.
- override 1:N을 다루지 못한다.

**회사 실제 계약서가 확보되면 §10의 M1 게이트에서 반드시 재검증한다.**
